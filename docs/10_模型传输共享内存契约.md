## 0. 一句话

模型进程把**每帧证据（512 B 固定结构）+ 活跃事件快照 + 原始 BGR 帧**写进一块
POSIX 共享内存；传输进程按需读，不需要 socket、不需要 JSON、不需要知道图像编码。

```
cameraApp ──/camera_shm (NV12, 已有)──> edge_infer ──/edge_infer_shm──> edge_tx(GRU)
                                             │                            │
                                      RKNN + 事件层                   载荷编码 / UDP
```

## 1. 内存布局

共享内存名：**`/edge_infer_shm`**，锁文件：**`/tmp/edge_infer.lock`**。
两端必须使用同一组常量（`src/edge_node/edge_shm.py` 与 C++ 头文件各持一份，
由自检脚本 `scripts/check_edge_shm.py` 校验一致）。

| 段 | 起始偏移 | 大小 | 说明 |
|---|---:|---:|---|
| Header | `0` | 128 B | 全局参数 + 计数器 |
| FrameRecord × 64 | `128` | 32,768 B | 逐帧证据环 |
| EventSnapshot × 16 | `32,896` | 3,072 B | 活跃事件表 |
| FrameImage × 8 | `35,968` | 7,373,056 B | BGR 原始帧环 |
| **合计** | | **7,409,024 B（≈7.07 MiB）** | |

所有数值**小端序**；RK3588 为 ARM64 小端，无转换。
所有结构体按 8 字节自然对齐设计，**不需要 `#pragma pack`**，C++ 编译器不会插入隐藏填充；
Python 侧用 `struct` 的 `<` 前缀即可得到相同布局。

概念上的"常量"：

```
MAGIC    = 0x45444731      # "EDG1"
VERSION  = 1
N_REC    = 64              # 逐帧记录槽数（15 fps 时约 4.3 s 历史）
N_EV     = 16              # 活跃事件槽数
N_IMG    = 8               # 帧环槽数（15 fps 时约 0.5 s 历史；主要用于回溯取帧）
```

Python：

```python
HDR_FMT = "<IIQ" + "I"*10 + "II" + "Q"*6 + "II" + "Q"   # 128 B
assert struct.calcsize(HDR_FMT) == 128
```

**读端启动校验**：`magic`、`version`、`total_size`、`n_rec/n_ev/n_img`、`img_w/img_h`

**存活判断**：`pub_seq` 在 2 s 内没有变化 → 打印"推理进程可能卡住/退出"，

## 3. FrameRecord（512 B）—— 核心契约

每个**推理帧**发布一条。非推理帧（`--stride` 跳过的）**不发布**，用 `frame_id`
跳变判断；推理失败也发布一条，`flags` 标 `BAD_FRAME`，其余字段清零。

| 偏移 | 类型 | 字段 | 说明 |
|---:|---|---|---|
| 0 | u64 | `seq` | 发布号 n（与发布时的 `header.pub_seq` 一致） |
| 8 | u64 | `frame_id` | 摄像头帧号，单调递增，可能跳号 |
| 16 | u64 | `capture_ts_ns` | 摄像头时间戳，见 §7；无效时填 0 |
| 24 | u64 | `publish_ts_ns` | 写端发布时刻（`CLOCK_MONOTONIC`） |
| 32 | f32 | `infer_ms` | 本帧从取帧到发布的耗时 |
| 36 | u32 | `flags` | 见 §6 |
| 40 | u16 | `n_det` | `dets[]` 中实际写入的条数（0~6） |
| 42 | u16 | `n_person` | 本帧 person 框总数（可能 > 6） |
| 44 | u16 | `det_total` | 本帧检测框总数（截断前） |
| 46 | u16 | `img_slot` | 本帧 BGR 在帧环中的槽位；`0xFFFF` = 无图 |
| 48 | f32×8 | `event_vector` | 8 维事件向量，布局沿用 `common.event_vector` |
| 80 | f32 | `aspect` | 主目标 高/宽 |
| 84 | f32 | `cx` | 主目标归一化中心 x |
| 88 | f32 | `cy` | 主目标归一化中心 y |
| 92 | f32 | `w` | 主目标归一化宽 |
| 96 | f32 | `h` | 主目标归一化高 |
| 100 | f32 | `area_ratio` | 主目标框面积 / 画面面积 |
| 104 | u32 | `best_event_id` | 当前最该关注的事件 id；`0` = 无 |
| 108 | u8 | `best_kind` | `EventKind` 数值 |
| 109 | u8 | `best_state` | `EventState` 数值 |
| 110 | u8 | `best_urgency` | `Urgency` 数值 |
| 111 | u8 | `flags2` | 保留，置 0 |
| 112 | f32 | `best_conf` | 事件层的 `confidence`（**不是概率**） |
| 116 | f32 | `best_reliability` | 校准后的可靠性；未校准时置 `-1` |
| 120 | u64 | `kind_first_ts_ns` | 当前 `best_kind` 首次出现的时刻（告警起点）；无则 0 |
| 128 | det×6 | `dets[6]` | 每项 24 B，见下 |
| 272 | 240 B | `reserved` | 必须置 0；新字段优先放这里，**不得改变已有偏移** |

`dets[i]`（24 B）：

| 相对偏移 | 类型 | 字段 |
|---:|---|---|
| 0 | u16 | `cls`（COCO，person = 0） |
| 2 | u16 | `pad`（0） |
| 4 | f32 | `conf` |
| 8 | f32 | `x1` |
| 12 | f32 | `y1` |
| 16 | f32 | `x2` |
| 20 | f32 | `y2` |

**入选规则**（写端负责，读端不要重排）：
1. 先按 `conf` 降序取所有 `cls == 0` 的 person 框，最多 6 个；
2. 不足 6 个时，用其余类别按 `conf` 降序补满；
3. `n_det = min(实际写入数, 6)`，`n_person` / `det_total` 统计的是**截断前**的总数。

Python：

```python
DET_FMT = "<HHfffff"                                   # 24 B
REC_FMT = ("<QQQQfIHHHH" "8f" "6f" "I" "4B" "ff" "Q"
           + DET_FMT[1:] * 6 + "240x")                 # 512 B
assert struct.calcsize(REC_FMT) == 512
```

> ⚠️ `DET_FMT[1:]`：子格式串拼进主串时要**去掉它自己的 `<`**，
> 否则 `struct.calcsize` 会报 `bad char in struct format`。

| 14 | u8 | `urgency` | `Urgency` |

| 40 | f32 | `confidence` | 当前置信度/规则分 |

## 5. FrameImage（32 B 头 + BGR 负载）

| 偏移 | 类型 | 字段 | 说明 |
|---:|---|---|---|
| 0 | u64 | `seq` | = 发布时的 `header.img_seq` |
| 8 | u64 | `frame_id` | 对应 FrameRecord 的 `frame_id` |
| 16 | u64 | `capture_ts_ns` | 同 FrameRecord |
| 24 | u32 | `w` | = `header.img_w` |
| 28 | u32 | `h` | = `header.img_h` |
| 32 | u8×`img_size` | `bgr` | **BGR 连续存储**，行跨度 = `w*3` |

```python
IMG_HDR_FMT = "<QQQII"                                 # 32 B
```

槽位 = `header.img_seq % n_img`。写端覆盖最老槽位时 `img_overwrites += 1`。
读端按 `frame_id` 二次校验：拷贝前后若 `frame_id` 变了，说明被覆盖，丢弃重读。

**为什么存 BGR 不存 NV12**：写端（模型进程）已经转好了；传输端直接裁 ROI 就能编码，
不必再学一遍 NV12。代价是写端多拷 921 KB（约 0.5~1 ms），换传输端省 5~8 ms 的
`cvtColor` —— 因为瓶颈在模型进程，这笔账是划算的。

**为什么图不塞进 FrameRecord**（记录 512 B，一帧 BGR 921,600 B，差 **1800 倍**）：

1. **读路径分层**：只做决策时读 512 B（15 fps 下 7.5 KB/s），决定发图才碰 921 KB（13.8 MB/s）；
2. **环深度不同**：记录 64 槽（4.3 s）vs 图 8 槽（0.5 s）；内联会让记录区涨到约 56 MiB，或把历史砍到 0.5 s；
3. **写入粒度**：512 B 微秒级、921 KB 约 0.5 ms；分开才能表达"有记录、没图"（坏帧/无框）；
4. **两级告警**：几十字节 metadata 单独就能报警，图是可选增强；
5. **结构体定长**：读端才能用 `seq` 直接算偏移。

读端必须用 `frame_id` 二次校验：`img_slot` 只负责定位，图可能已被 8 帧之后的写覆盖。
`img_slot == 0xFFFF` 表示无图；`frame_id` 不匹配时必须退回最新帧或跳过，**不能按槽位盲读**。

### 5.1 帧环不是"片段缓冲"（重要）

帧环只有 8 槽（15 fps 约 0.5 s），它只回答一个问题：**"事件这一刻的图在哪"**。
跌倒前后的视频片段**不从这里取，也不要因此扩大这个环**：

- 片段需要 8~10 s 的**事前**缓冲（事件发生时，画面已经过去了，必须回看）；
- 把帧环扩到 150 槽，shm 会从 7 MB 涨到 **130 MB**，而且模型进程每帧要多拷 921 KB——
  它已经单核饱和，这笔开销不能加在它身上；
- 正确做法：**传输进程自己维护一个滚动 JPEG 环**（320×240~480×360，8~10 s 约
  1.5~4 MB）。平时每帧读帧环 → 缩小 → JPEG 存环；事件触发时按 `kind_first_ts_ns`
  切窗口（前 3 s + 后 3 s），直接以 **M-JPEG** 发送——每帧独立，丢一包只坏一帧。

由此带来的两个成本，读端要有预期：

1. 传输进程必须**每帧都读帧环**（即使决定不发送），约多占单核 2~3%；
2. 片段是**报警之后**的低优先级载荷：metadata → ROI → FULL → CLIP，
   信道不够时丢 CLIP，不影响报警。

分工可以概括成：**模型层负责"事件这一刻的证据"，传输层负责"事件前后的叙事"。**

## 6. flags 位定义

`FrameRecord.flags`：

| 位 | 名称 | 含义 |
|---:|---|---|
| 0 | `INFERRED` | 本帧成功推理 |
| 1 | `BAD_FRAME` | 解码/推理失败，其余字段无效 |
| 2 | `NO_PERSON` | 本帧没有 person 框 |
| 3 | `TS_FROM_CAMERA` | `capture_ts_ns` 来自摄像头；未设置时该字段是写端补的时刻 |
| 4 | `TRACKER_ERROR` | 事件层异常，`best_*` 字段不可信 |

`Header.flags`：

| 位 | 名称 | 含义 |
|---:|---|---|
| 0 | `MODEL_READY` | RKNN 初始化完成，开始发布 |
| 1 | `MODEL_EXITED` | 写端正常退出 |

## 7. 单位与无效值（**最容易被读端误解的地方**）

1. **时间**：全部是 `CLOCK_MONOTONIC` 纳秒。`capture_ts_ns` 来自 cameraApp 的槽头；
   若其 `ts_flags` 表明时间戳无效，写端填 0 并**不置** `TS_FROM_CAMERA`，
   用 `publish_ts_ns` 减自身收帧时刻代替。
2. **坐标**：归一化到**旋转后的摄像头原图**（当前 480×640），**不是** 640×640 的
   letterbox 图。读端不要自己再归一化一次。
3. **置信度**：`[0,1]` 的 float32。`best_conf` 是事件层分数（可能是规则分），
   `best_reliability` 才是校准概率；后者未校准时为 `-1`，**不要当 0 用**。
4. **无效值**：禁止写 `NaN` / `Inf`。无框 → `n_det=0`，`dets` 清零；无事件 →
   `best_event_id=0`，`best_*` 清零。
5. **主目标**：`aspect/cx/cy/w/h/area_ratio` 描述的是 `event_vector` 里那一个
   主目标（severity 最高），不是 `dets[0]`（`dets[0]` 是 conf 最高的 person）。
6. **事件 id ≠ 记录 seq**：`event_id` 是事件层内部 id，跨帧稳定；`seq` 是发布序号。

## 8. 发布 / 读取协议

> 本节写的是**写端的发布顺序**，以及一种可行的读法。读端的具体实现（通知方式、
> 循环结构）属于控制端，不由本契约规定；两边必须对齐的只有互斥机制，以及
> "`pub_seq` 可见时记录与图已完整"这个语义。

### 8.1 锁

两块共享内存都用 **同一个 `flock` 文件锁**（`/tmp/edge_infer.lock`）保护：

- 写端每次发布持有排他锁，**持锁时间必须 < 1 ms**（结构体写入 + 一次 memcpy）；
- 读端拷贝期间持共享锁或排他锁均可，拷贝完立刻释放；
- C++ 用 `flock(fd, LOCK_EX)`，Python 用 `fcntl.flock`。两者操作同一个 inode，
  是这个场景下最省事、语言无关的互斥方式。

> 为什么不只用 seqlock：ARM64 是弱内存序，Python 无法表达 acquire/release 屏障，
> "写完 seq 再写数据"可能被 CPU 重排，读端会读到"新序号 + 旧数据"。
> 15 Hz 下 `flock` 的开销可以忽略，正确性白送。

### 8.2 写端（模型进程）

```
for each inferred frame:
    rec = build_record(...)          # 纯内存，< 50 us
    img_off = 32 + (header.img_seq % n_img) * (32 + img_size)
    lock():
        # 先写图像（读端可能正在等新图）
        put_u64(img_off, header.img_seq)      # 先占位，最后改成自己的 seq
        memcpy(img_off + 32, bgr, img_size)
        put_u64(img_off + 0, img_seq + 1)
        put_u64(img_off + 8, frame_id)
        put_u64(img_off + 16, capture_ts_ns)
        header.img_seq += 1
        if img_seq >= n_img: header.img_overwrites += 1
        # 再写记录
        n = header.pub_seq + 1
        rec_off = 128 + ((n - 1) % n_rec) * rec_size
        pack_into(rec, rec_off, ..., seq=n, ...)
        header.pub_seq = n
        header.last_update_ts_ns = now_ns
    unlock()
```

顺序要求：**图像先完成，再让 `pub_seq` 可见** —— 读端拿到记录时，
`img_slot` 指向的图一定已经写完。

### 8.3 读端（传输 / GRU）

```
h = read_header()                  # 启动时校验 magic/version/尺寸
last = 0
loop:
    if h.pub_seq == last: sleep(1~2 ms); continue
    lock():
        n = h.pub_seq
        gap = n - last
        if gap > n_rec: 丢历史，last = n - n_rec + 1
        for k in range(last + 1, n + 1):
            rec = unpack(rec_off(k))
            assert rec.seq == k    # 不一致说明被覆盖，跳过
            yield rec
        last = n
    unlock()
```

- **`gap > 1` 表示中间漏了记录**（写端跑得比读端快，或读端被调度阻塞）；
  `gap > n_rec` 表示漏掉的数据已被覆盖，只能从最新的开始。
- 需要"最近 N 帧轨迹"时，直接用 `pub_seq - N + 1 .. pub_seq`，不要自己维护缓存。
- 需要事件对应的图时，用 `FrameRecord.img_slot` 直接定位；需要**更早**的帧
  （例如 `kind_first_ts_ns` 那一帧）时，扫描帧环按 `frame_id` 匹配，
  找不到说明已被覆盖 → 退回 `img_slot` 的最新帧。

## 9. 两端各自的实现要点

### Python（写端 / 读端同一份模块）

```python
import mmap, os, struct, fcntl

fd = os.open("/edge_infer_shm", os.O_RDWR | os.O_CLOEXEC)
mm = mmap.mmap(fd, 0)                     # 写端需先 ftruncate 到 total_size
lock_fd = os.open("/tmp/edge_infer.lock", os.O_RDWR | os.O_CREAT, 0o666)
fcntl.flock(lock_fd, fcntl.LOCK_EX)

# 图像零拷贝视图（只读用途不要改内容）
img = np.frombuffer(mm, np.uint8, count=img_size, offset=img_off + 32)
img = img.reshape(img_h, img_w, 3)        # cv2.imencode 可直接吃
```

注意：
- `struct.pack_into` / `unpack_from` 直接操作 `mmap`，不要先 `bytes(mm)` 全量拷贝；
- 写端 `np.frombuffer(mm, ...)` 得到的是可写数组，若要画框请先 `.copy()`，
  否则会把标注烧进共享内存；
- `mmap` 在进程退出后由内核回收，槽位里残留旧数据是正常的 —— 读端必须靠
  `seq` / `frame_id` 校验，不能假设槽位一开始是空的。

### C / C++（读端）

**不要照本文手抄结构体** —— 直接 `#include "edge_shm.h"`（`src/edge_node/edge_shm.h`，
C11，常量/结构体/偏移/`_Static_assert` 都在里面）。它的名字都带 `edge_` 前缀，
不会和 camera 侧的 `image_frame` / `shm_message` / `camera_shm` 冲突。
头文件已用 `-Wall -Wextra -Wshadow -Wconversion -Wsign-conversion -Wcast-qual -Werror`
编译通过（即 cameraApp 的告警集）。

其内容等价于下面这段；若一定要自己写，也必须保留 `_Static_assert`：

```cpp
#pragma pack(push, 1)   // 本布局已自然对齐，加不加结果相同；加上更保险
struct FrameRecord {
    uint64_t seq, frame_id, capture_ts_ns, publish_ts_ns;
    float    infer_ms;
    uint32_t flags;
    uint16_t n_det, n_person, det_total, img_slot;
    float    event_vector[8];
    float    aspect, cx, cy, w, h, area_ratio;
    uint32_t best_event_id;
    uint8_t  best_kind, best_state, best_urgency, flags2;
    float    best_conf, best_reliability;
    uint64_t kind_first_ts_ns;
    struct { uint16_t cls, pad; float conf, x1, y1, x2, y2; } dets[6];
    uint8_t  reserved[240];
};
#pragma pack(pop)
static_assert(sizeof(FrameRecord) == 512, "FrameRecord layout drift");
```

- 用固定宽度类型（`uint64_t` 等），不要 `unsigned long`（宽度随平台变）；
- 不要用 `bool`（C++ `bool` 与 Python 字节宽度约定不直观），用 `uint8_t`；
- `static_assert` 是强制的：布局漂移在编译期就该炸，而不是运行时读到垃圾。

## 11. 自检（写端交付物之一）

`scripts/check_edge_shm.py`（✅ 已实现），纯 Python、不需要板子：

1. 用 `struct.calcsize` 断言所有格式串长度 = 128 / 512 / 192 / 32；
2. 建一块临时 shm（或普通 mmap 文件），写一条合成记录再读回，逐字段比对；
3. 模拟读端落后：连写 `n_rec + 5` 条，验证 `gap` 分支与 `seq` 不一致的跳过逻辑；
4. 模拟帧环覆盖：写 `n_img + 2` 帧，验证 `img_overwrites` 与 `frame_id` 校验；
5. 打印一条记录的十六进制 dump，方便和 C++ 侧人工比对。

> 这套自检就是"契约测试"：队友的 C++ 读端只要能被同一份 dump 解析，布局就对齐了。

## 12. 变更规则

1. **偏移冻结**：已有字段的偏移和宽度永不改变；
2. 新增字段 → 用 `reserved`，并在文档里登记偏移；
3. 删除/改类型 → `version + 1`，读端遇到不认识的版本必须拒绝启动；
4. 新增事件类型/紧急度 → 只改数值表，不改结构体；
5. 任何布局变更都要同步改 `edge_shm.py`、C++ 头文件的 `static_assert`、自检脚本 ——
   三处任一没改，自检要能炸出来。

## 13. 字段用途速查（谁读、什么时候读）

> `v1` 一列表示"一直传"的第一版是否已经会用到。没用到不代表可以删 ——
> 偏移一次定死，比以后加字段便宜得多。

| 字段 | 写入者 | 读端用途 | v1 |
|---|---|---|:--:|
| `seq` | 模型 | 漏帧检测（`gap`）、历史窗口定位、覆盖判定 | ✅ |
| `frame_id` | 模型（来自摄像头） | 与帧环配对、stride 跳帧识别、远端结果指认、评测对齐真值 | ✅ |
| `capture_ts_ns` | 摄像头 | **端到端时延起点**；`publish − capture` = 板上处理时延 | ✅ |
| `publish_ts_ns` | 模型 | 发布到发送的排队时延、心跳 | ✅ |
| `infer_ms` | 模型 | 性能监控；GRU 状态向量里"NPU 负载"的代理量 | ✅ |
| `flags` | 模型 | 区分"没人"与"没推理成功"，防止把 0 当有效数据 | ✅ |
| `n_person` / `det_total` | 模型 | GRU 的"目标数""场景复杂度" | ✅ |
| `n_det` | 模型 | `dets` 的循环上界；`det_total > n_det` 说明发生了截断 | ✅ |
| `img_slot` | 模型 | 直接定位本帧 BGR，无需扫描帧环 | ✅ |
| `dets[6]` | 模型 | 裁 ROI、多人择优、远端 pose 输入框、demo 画框 | ✅ |
| `event_vector[8]` | 事件层 | GRU 的直接输入；与离线 traces 同格式，便于复现实验 | ✅ |
| `aspect` | 模型 | 单帧规则基线（已知 AUC 0.97）；severity 的组成 | ✅ |
| `cx, cy, w, h` | 模型 | 还原主目标框 `x1=cx−w/2 …`；跨帧算下沉/变扁 | ✅ |
| `area_ratio` | 模型 | GRU 状态向量"面积占比" | ✅ |
| `best_event_id` | 事件层 | 调度优先级、远端回传指认、同一次跌倒去重 | ✅ |
| `best_kind` / `state` / `urgency` | 事件层 | 调度决策输入；线上协议直接用 | ✅ |
| `best_conf` | 事件层 | 排序与工作点选择（**不是概率**） | ✅ |
| `best_reliability` | 事件层 | "值不值得占带宽"；未校准为 `-1` | ⬜ |
| `kind_first_ts_ns` | 事件层 | 告警起点：提前量评测、检测延迟、deadline 起点 | ⬜ |
| `EventSnapshot` 全表 | 事件层 | 同时看多个事件；`peak_confidence` / `hits` 供复盘与校准 | ⬜ |
| `FrameImage` | 模型 | 远端确认的 ROI / FULL 载荷来源 | ✅ |
| Header 计数器 | 模型 | 实验指标：处理是否跟得上、读端落后几次、坏帧率 | ✅ |

**注意两套字段的分工**：`event_vector` 是**逐帧检测快照**，`best_*` 是**事件语义**。
`TRACK_LOST` 帧没有框 —— `event_vector` 会是 `NONE_EVENT`（`has_event=0`），
但 `best_kind = TRACK_LOST`。这正是"检测器失效本身是信号"的落点，两者不能互相替代。

## 14. 明确不放进结构体的东西

- 变长字符串、JSON、事件名 —— 一律用枚举数值；
- 图片编码结果（JPEG）—— 编码属于传输端职责，见 §5；
- 信道状态（RSSI/RTT/丢包）—— 传输端自己知道，不需要模型回传；
- GRU 状态向量 —— 由读端用 `event_vector` + 特征 + 信道字段自行拼装；
- 每帧的原始检测框超过 6 个 —— 截断并靠 `det_total` 说明。
