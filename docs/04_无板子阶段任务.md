  `EventType` 枚举（NONE / PERSON / SUSPECTED）；`NONE_EVENT` 作无人帧规范表示。

- `scripts/check_event_vector.py` — 合成数据自检，**不依赖 ultralytics/torch**，
  任何环境可跑：往返一致 / severity 合成 / 多人挑主目标 + 类别阈值过滤。
- `scripts/check_event_vector_real.py` — 真实模型输出验证（需 rk 环境）：
  确认 `boxes.xyxyn/conf/cls` 取值路径、dtype、归一化范围，
  并验两条入口（Results 路径 vs numpy 路径）结果一致。

**2026-09-11 加固**（代码审查发现的问题，详见 `docs/06_问题记录.md`）：
- `EventVector` 加 `@dataclass(frozen=True)`。`NONE_EVENT` 是模块级共享单例且被
  `is` 比较，可变时任何一处原地赋值都会污染全进程的「无人帧」语义。
- 新增 `common.event_vector.to_numpy()`：鸭子类型（detach/cpu/numpy）而非
  `isinstance(torch.Tensor)`，保持本模块**不依赖 torch**（否则合成自检就不能在
  任意环境裸跑）。`event_from_result` 里三处 `.cpu().numpy()` 改用它 ——
  **RK3588 板端 RKNNLite 的输出是 numpy，硬写 `.cpu()` 会直接 AttributeError**。
- 新增 `src/common/metrics.py` + `scripts/check_metrics.py` — 评测的「尺子」：
  ROC 并列分组、秩公式 AUC、ties 体检、max/mean/top3mean 聚合。纯 numpy 可裸跑。
- 新增 `src/common/cache.py` + `scripts/check_cache.py` — 缓存/权重的版本机制：
  文件名带特征集身份 + 内容指纹（含全部归一化常数）+ 加载即严格校验。

**关键设计决定**：
- 一帧只表征「最严重的主目标」，多人取 severity 最高者（不是置信度最高者）。
- `severity = 置信度 × 高宽比异常度`，低置信自动打折，抑制鬼影框误报。
  高宽比 ≥1.5 视为直立（异常度 0），≤0.7 视为躺卧（异常度 1），中间线性插值。
- 时序判定（高宽比突变 / 停留超时 / 位置异常）**不在此层**，属 GRU 职责，
  边缘端只出向量、不做通信决策。

实测（`bus.jpg` / `zidane.jpg`，见 `docs/07`）：直立行人 h/w 1.9~3.8 → severity 0，
判 PERSON 不触发卸载；zidane 那个 h/w=0.91 的扁框 → severity 0.611 → SUSPECTED；
空帧 → 全零向量。非 person 类（bus/tie/stop sign）均被正确忽略。

> ⚠️ 已知局限：`zidane.jpg` 里那位其实是**站着**的，只因上半身占满画面、
> 下半身被画面边缘截断，h/w 才降到 0.91 被判 SUSPECTED。
> 说明**纯高宽比无法区分「真跌倒」与「框被边缘截断」**。这不是 bug，
> 是单帧几何量的固有上限 —— 恰好是 T0.6 引入 GRU 的动机：
> 截断框会持续多帧稳定存在，而跌倒是高宽比的突变，时序可分。
> 记录在 `docs/06_问题记录.md`。

**2026-09-11 · 时序特征与消融（前置工作已就绪）**：
把「跑模型」和「算特征」拆开，之后调特征是秒级、不再回头碰模型：

```bash
python scripts/gru_features.py list                    # 看有哪些特征集
python scripts/gru_features.py frames --mode det       # 原始帧表（跑模型，~1.5 min）
python scripts/gru_features.py frames --mode pose      # 姿态帧表（~4 min，唯一慢步骤）

```

- `scripts/gru_features.py` — 原始帧表（每帧 13 列原始量，含 bbox 位置/面积）+
  5 个特征集注册表：`det.v1`(4) / `det.v2a`(6) / `det.v2`(8) / `pose.v1`(6) / `pose.v2`(10)。
  新增的 4 维是框中心下沉比 `cy_drop` 与尺度突变比 `size_log_ratio`（相对**因果基线**，
  只取当前帧之前的最近 30 个有目标帧的中位数），把「瞬态 vs 平稳」直接写进特征。
- `scripts/check_features.py` — 8 组定点断言（突变亮起/躺稳归零/断裂保护/扩展关系…），
  比指标数字更能证明特征写对了。
- `train_gru_fall.py` 改为只消费特征缓存，支持 `--featsets` 任选组合做消融。

**实测结论**（docs/08 §9.3 §9.4，URFD 70 段）：

- 补回位置/面积后 det 的 GRU AUC 0.900→0.932，方差减半。
- 随机划分下样本量太小（每 seed 只有 8 段跌倒测试视频，AUC 刻度 0.0125），
  已补 **LOVO + 配对自助法**：
  ```bash
  python scripts/train_gru_fall.py --protocol lovo --out-json experiments/results/metrics_lovo.json
  python scripts/analyze_lovo.py     # 置信区间
  ```
- **关键结论：`pose.v2 − det.v2` 的 AUC 差只有 +0.0033（p≈0.875，CI 跨 0）——
  没有证据表明需要姿态。**边缘端只靠 yolov8n 检测特征 + 时序就够，可以省掉
  姿态卸载。（原先「det ≈ pose 打平」与后一轮「姿态略胜」两个说法都不成立，
  正确答案是「证据不足以区分，但足以支持不需要」。）
- **@FPR=0 不应再作主口径**：它由 40 段日常里分数最高的一段决定，不同特征集的
  阈值被不同视频顶上去。后续以 AUC 为主。

  零个负样本 → AUC 与 @FPR=0 都算不出来。原设想「重跑一遍就能对照」不成立，

**⚠ 2026-09-18 · 重大更正：现有 URFD 数据是 [深度|RGB] 拼接图**

为验证「躺地检测失效」在 URFD cam0 上是否也存在，逐帧比对时发现

**70 段全部是「左半深度图 + 右半 RGB」的左右拼接**。

判据（劈开送 YOLO）：左半饱和度 0.4 → 检出 0 个目标；右半饱和度 42.9 →
检出 `person 0.91`。

**后果**：横向人只占一半宽 → **`aspect = h/w` 被系统性放大一倍**（实测比值恒 0.50）。

| 阶段 | 中位 aspect | **h/w ≤ 0.7 占比** |
|---|---|---|
| 未躺地 | 3.65 | 0.0% |
| 跌倒中 | 1.83 | 2.4% |
| **躺地** | **0.71** | **49.6%** |

对照拼接图：躺地 ≤0.7 只占 **0.1%** —— **差 500 倍**。

→ **§3「单帧高宽比触发器漏检 90%、原因是低位视角」很大程度上是格式假象。**
→ **§9 的立项动机（「单帧规则不行所以需要 GRU」）强度需重新评估。**
→ §10 / §11 用别的数据（干净 RGB），不受影响。

**顺带拿到**：URFD 官方逐帧标注（`urfall-cam0-falls.csv` / `-adls.csv`，
label: -1未躺地 / 0正在跌倒 / 1躺地），与现有视频帧号严格对齐，已解到

|---|---|---|

| ADL 误触发 | 0/40 | 5/40（12%） |

**立项叙事要改写**：GRU 的价值不是「把瞎猜救回来」，而是**在 0.89 的强基线上
再显著提升**（零误报工作点召回 53%→87%）。另外 `det.v1` 上 GRU 增益几乎为零
（+0.002）—— **「补上框的位置/尺度」是 GRU 能发挥的前提**。

**pose 也复跑了，§9.4「不需要姿态」仍成立**：`pose.v2 − det.v2 = +0.0242`
（95%CI [−0.0045, +0.0676]，p≈0.200）不显著。但下界贴着 0（旧数据 −0.0313），
所以是「证据不足以区分」，离「有证据支持不需要」更远了一点。

**再换一个数据集（MCF）交叉检验**：

| 数据集 | 单帧基线 AUC | GRU AUC | **GRU 增益** |
|---|---|---|---|
| URFD 旧拼接图（无效） | 0.5500 | 0.9500 | +0.4000 |
| **URFD 干净 RGB（平视）** | **0.8908** | 0.9692 | **+0.0783** |
| **MCF（高地俯视 + 鱼眼）** | **0.5278** | 0.8770 | **+0.3492** |

**规律：GRU 本身在三个场景下都稳定在 0.88~0.97，变的是单帧基线 —— 而基线强弱
由相机视角决定。** 所以准确表述是「**需不需要 GRU 取决于部署机位**」，
不是单一结论。这对 T0.4（固定规则卸载）有直接指导：**先定机位，再定方案**。

详见 docs/08 §13。

**2026-09-18 · 重标定远端 judge 阈值（判断姿态值不值）**

judge 的三条阈值是在**旧拼接图数据**上定的（第①条在旧数据上命中率仅 0.1%，
形同虚设）。用官方逐帧标注 + 留一嵌套标定重做：

- 现行阈值视频级 AUC **0.7650** → 重标定后 **0.9458**（网格 0.9487，几乎一样 → 稳）
- **但消融：只用框线索 0.9604 > 加姿态 0.9458** —— 姿态没贡献，加了还略降
- **顺带：`severity` 反而不如直接用 `aspect`**（0.8917 vs 0.9604）——
  躺地时置信度本就偏低，要求高置信度恰好滤掉最想要的帧

**对「要不要 GRU」的冲击**：标定过阈值的单帧 `aspect` 规则 AUC **0.9708**，
与 GRU（0.9617~0.9767）**打平**（−0.0017，p≈0.55 不显著）。GRU 的增量只剩
零误报工作点的召回（80% → 96.7%）。

→ **§13.4 的「GRU 增益 +0.0783」基线是未标定的固定阈值；基线选谁，结论完全不同。**

**2026-09-18 · 在 MCF 上复检 —— 立项叙事最终定型**

同口径嵌套标定（按场景留一）：

| 数据集 | 最好的单帧规则 | GRU | GRU 优势 |
|---|---|---|---|
| URFD cam0（平视） | **0.9708** | 0.9692 | −0.0017（打平） |
| MCF（高位俯视） | **0.7594** | 0.8770 | **+0.1176** |

**换视角：单帧掉 0.21，GRU 只掉 0.09。**

机制证据：`severity` 的最优阈值在 8 个机位间差 **15×**（0.01~0.15）；即便

是有效工作点随机位漂移。**

→ **立项叙事：GRU 的价值在「跨视角稳定性」，不在单数据集峰值 AUC。**
