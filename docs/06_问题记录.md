## 已解决

- [x] 是否需要自己训练 YOLOv8n？→ 不需要，用 COCO 预训练模型直接检测人。
- [x] Windows 能否跑 rknn-toolkit2？→ 不能，需 WSL2/Linux；但算法部分可直接在 Windows 跑。
- [x] 2026-09-11 **AUC 算错了**：`roc()` 用不稳定的 `np.argsort` 排序，而单帧基线分数
      70 段里 67 段并列在 0.0，并列样本先后任意 → AUC 成了排序的副产品（打乱输入
      顺序可在 0.20~0.84 之间跳）。det 单帧的真实 AUC 是 **0.537**（≈随机），
      docs/08 §8.4 里的 0.715 是系统性虚高。已修：并列块只产生一个工作点 + 秩公式
      独立校验，回归测试见 `scripts/check_metrics.py`。详见 docs/08 §9.1。
- [x] 2026-09-11 **训练结果依赖隐式的数据顺序**：所有窗口按视频在字典里的顺序拼成
      大数组再打乱成批次，而那个顺序取决于缓存文件里条目的写入顺序（"先 fall 后
      adl"还是反过来）。换台机器重跑就可能对不上。已修：`split_videos` 的两个返回
      列表都显式排序，修后连跑两遍逐位一致。详见 docs/08 §9.2。
- [x] 2026-09-11 **帧表存四舍五入值导致判定在阈值边界翻转**：`process_frame` 调
      `judge()` 用原始几何量，写日志却存四舍五入值（torso 1 位、hip_ankle 3 位）。
      实测 45.04° 存成 45.0 后 `>45°` 从命中变不命中，4/70 段单帧基线对不上。
      已修：`process_frame` 额外带出 `*_raw` 原始精度字段，帧表存原始值，四舍五入
      收回 v1 特征配方。
- [x] 2026-09-11 **缓存静默复用**：`load_or_extract` 原来只判断"文件存在"就读。
      维度变了、或更隐蔽的"维度没变而常数变了"（如 clip(aspect,0.3,4)/4 改成
      clip(aspect,0.5,3)/3 仍是 1 维）都会读到旧缓存，跑出一份看起来正常但毫无
      意义的结果。已修：文件名带特征集身份 + 内容指纹（含所有归一化常数）+
      加载即严格校验，见 `src/common/cache.py`。

- [x] 2026-09-12 **URFD 的 cam1 做不了 AUC**：两台相机不对称 —— cam1 只有 30 段跌倒，
      **没有任何 ADL**（40 段日常只用了 cam0）。所以 cam1 上零个负样本，AUC 与
      @FPR=0 都算不出来，只剩召回率、而没有误报率配套时它没有意义（阈值调到 0
      就是 100%）。**原计划「cam1 当免费对照、重跑一遍就能回答换视角是否成立」
      不成立**。已改做不需要负样本的**检测率**对比，见 docs/08 §10.3。
- [x] 2026-09-12 **cam1 的检测率显著更差**：30 段配对，cam0 均值 87.2% vs cam1
      69.0%，配对差 −18.2%，**24/30 段 cam1 更差**（符号检验 z=3.29）。且 cam0
      的 30 段全部从第 0 帧就检到人，cam1 平均要等 15 帧（最长 82 帧）——
      吸顶相机**视野窄**。**视角的影响主要落在检测环节，不在时序模型环节**，
      所以换视角的第一优先级是检测召回，不是重训 GRU。详见 docs/08 §10.3。
- [x] 2026-09-12 **URFD 两视角并不可靠地时间同步**：用与视角无关的运动能量互相关
      估计，**只有 15/30 段同步**（|lag| ≤ 5 帧），**6/30 段偏 ≥ 16 帧**
      （最大 −99 帧 ≈ 3.3 s）。fall-19 是在 r=0.971 下取到 −72 帧，相关性这么高
      说明偏移是真的。URFD 官方的同步文件（`fall-XX-data`）本仓库没有。
      → **跨视角做配对比较必须先按段校正偏移**，否则 6/30 段在比不同时刻。
      详见 docs/08 §10.4。
- [x] 2026-09-12 **`cy_drop` 的跨视角可比性受取景影响**：`cy_drop` 是相对基线的
      **比值**，取景一变分子分母同时变。现有 cam0 mp4 来自 GitCode 镜像、是
      640×240（原始 640×480 被裁过），**不能**直接与原始 cam1 对比 —— 差异里会
      混进裁剪的贡献。已改为两视角都用同一批原始帧、同一套预处理
      （`scripts/prepare_urfd_views.py`，见 docs/08 §10.1）。
