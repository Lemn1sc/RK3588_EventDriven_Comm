# 事件层接口（T0.10）

> 状态：✅ 第一版（2026-11-16）  
> 负责人：事件端（Lemn1sc）  
> 边界：本层只负责**事件形成 + 证据 + 可靠性 + 载荷**；**不做**通信调度、不做 GRU 决策、
> 不改 8 维事件向量布局。调度与协议由控制端/队友负责，接口见 §7。

---

## 1. 这一层解决什么

现有脚本输出的是**逐帧行**：

```
frame=1052 has_event=1 confidence=0.80 aspect=2.45 severity=0.00
```

但控制端要调度的是**事件**：

```
event_id=7 kind=SUSPECTED_FALL state=ACTIVE start=1052 last_seen=1081
confidence=0.52 suggested_urgency=HIGH reliability=0.31
```

差别不只是“聚合”：

1. **生命周期**：一次跌倒横跨几十帧，控制端只需要 start/update/close，不需要每帧一行；
2. **不确定性**：低置信躺姿不再被 `severity<0.5` 丢掉，而是变成“高紧急度 + 低可靠性”
   的事件，由调度器决定是否用小包先抢通；
3. **失效即信号**：人躺地后检测器失效，事件层输出 `TRACK_LOST`，而不是和“本来没人”
   一样都变成 `NONE`；
4. **载荷选项**：同一事件有 metadata / ROI / FULL / CLIP 四档，供控制端按信道和
   deadline 选。

## 3. 数据模型

### 3.1 `Evidence`（一帧里的一条证据）

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | `EventKind` | 证据类型（见 §4） |
| `confidence` | float 0~1 | 来源自己的置信度 |
| `bbox` | `(x1,y1,x2,y2)` 或 None | 归一化 xyxy；自动排序、裁剪 |
| `source` | str | `detector` / `track_lost` / `foreground` / `remote_pose` … |
| `reliability` | float 或 None | 校准后的“事件为真”概率（可选，事件层透传） |
| `meta` | dict | 证据来源的附加信息（如 aspect、触发原因） |

### 3.2 `Event`（一个持续存在的事件）

| 字段 | 说明 |
|---|---|
| `event_id` | tracker 内单调递增；同一次跌倒的升级保留同一个 id |
| `kind` / `kind_id` | 当前类型；只升不降 |
| `state` / `state_id` | `CANDIDATE / ACTIVE / CONFIRMED / EXPIRED` |
| `start_frame` / `start_ts` | 事件**第一次出现**（可能是 PERSON） |
| `end_frame` / `end_ts` | **最后一次证据**的帧/时间，不是关闭时间 |
| `closed_frame` | 因断档/TTL 关闭的帧；`null` 表示还在进行或输入结束 |
| `confidence` / `peak_confidence` | 当前 / 峰值置信度 |
| `reliability` | 校准后可靠性（若来源提供） |
| `suggested_urgency` / `urgency_id` | 事件层给控制端的**建议**紧急度 |
| `bbox` | 最后一次的位置 |
| `sources` | 参与过该事件的证据来源 |
| `hits` / `missed_frames` | 命中次数 / 连续未命中帧数 |
| `kind_first_frame` / `kind_first_ts` | **每种类型第一次出现**的帧/时间（见下） |
| `kind_confidence` | **每种类型第一次出现时的 confidence**；事件最终 confidence 会被后续证据覆盖，复盘 TRACK_LOST 分数必须看这里 |
| `meta` | 最近一条证据的解释字段（`dy` / `d_aspect` / `score` / `reasons` …） |

> `kind_first_frame` 是调度和评测的关键。一个人可能先作为 `PERSON` 出现 2 秒，然后才升级成
> `SUSPECTED_FALL`。事件的 `start_frame` 是前者，`kind_first_frame["SUSPECTED_FALL"]`
> 才是**告警起点**。用 `start_frame` 算提前量会虚报预警时间。
>
> `kind_confidence` 同理：事件最终的 `confidence` 是“最后一次证据”的分数，TRACK_LOST
> 之后如果又来了一个检测框，最终分数会被覆盖。想按“TRACK_LOST 当时的可靠性”过滤，
> 必须看 `kind_confidence["TRACK_LOST"]`。评测脚本的 `--min-confidence` 就是按这个口径。

### 3.3 生命周期

```
candidate ──(命中 >= min_hits)──> active ──(收到 FALL_CONFIRMED)──> confirmed
    │                                  │
    └──── gap > max_gap / age > ttl ───┴──> expired
```

- `max_gap_frames` 默认 30（约 1s@30fps）：证据断档超过该帧数就关闭；
- 断档用**帧号差**判断，不是“连续未命中计数”——帧表可能跳过未标注区间；
- `ttl_frames` 默认 300（约 10s）：防止陈旧告警无限堆积；
- 事件只升不降：`PERSON → TRACK_LOST → SUSPECTED_FALL → FALL_CONFIRMED` 保留同一 id，
  避免同一次跌倒被拆成多个事件、重复计数。

### 3.4 `EventUpdate`（事件流消息）

```json
{
  "action": "UPDATE",
  "action_id": 1,
  "frame_index": 1083,
  "timestamp": 36.1,
  "reason": "ACTIVE/PERSON → ACTIVE/SUSPECTED_FALL",
  "event": {
    "event_id": 7,
    "kind": "SUSPECTED_FALL",
    "kind_id": 4,
    "state": "ACTIVE",
    "state_id": 1,
    "start_frame": 1052,
    "end_frame": 1083,
    "start_ts": 35.07,
    "end_ts": 36.1,
    "duration_s": 1.03,
    "confidence": 0.52,
    "peak_confidence": 0.71,
    "reliability": 0.31,
    "suggested_urgency": "HIGH",
    "urgency_id": 3,
    "bbox": [0.42, 0.55, 0.71, 0.78],
    "sources": ["detector", "track_lost"],
    "hits": 12,
    "kind_first_frame": {"PERSON": 1052, "SUSPECTED_FALL": 1083},
    "kind_first_ts": {"PERSON": 35.07, "SUSPECTED_FALL": 36.1},
    "kind_confidence": {"PERSON": 0.71, "SUSPECTED_FALL": 0.52}
  }
}
```

`action`: `START` / `UPDATE` / `CLOSE`。控制端应消费事件流，而不是逐帧行。

## 4. 事件类型与建议紧急度

| kind | 含义 | 建议紧急度 | 典型来源 |
|---|---|---|---|
| `PERSON` | 检测到人，姿态/行为正常 | LOW | detector |
| `PERSON_ABNORMAL` | 停留超时、姿态异常，但未到跌倒疑似 | MEDIUM | detector / 规则 |
| `TRACK_LOST` | 之前跟踪到的人突然消失（消失前有下沉/变扁时分数更高） | MEDIUM；score ≥0.55 时 **HIGH** | track_lost |
| `SUSPECTED_FALL` | 低置信躺姿、轨迹消失+下沉、前景大 blob | HIGH | detector / track_lost / foreground |
| `FALL_CONFIRMED` | 远端姿态 / 人工确认 | CRITICAL | remote_pose |
| `BACKGROUND` | 心跳、遥测 | BACKGROUND | 控制端/系统 |

原则：**漏报代价高的类型给高紧急度，不按检测置信度打折**。低置信躺姿恰恰是最需要
远端确认的情况。事件层只给“建议”，最终由控制端结合信道/队列/截止时间决定。

来源还可以只调紧急度、不改类型：`Evidence.urgency` 只升不降。例如高分的 `TRACK_LOST`
建议 HIGH，但保留“人突然消失”的语义，不假装它已经是 `SUSPECTED_FALL`。

### 4.1 TRACK_LOST 评分（2026-11-16 改进）

旧逻辑只要“短断档 + 连续命中”就发一条固定 0.2 的 `TRACK_LOST`，于是 URFD 的 ADL
结尾（人正常走出画面）产生大量误报。现在改成**消失前运动特征打分**：

```
score = 0.15
      + 0.45 * clip(d_aspect / 1.0)
      + 0.30 * clip(dy / 0.15)
      + 0.10 * (1 if 不贴边 else 0)
```

- `d_aspect = aspect_ref − aspect_last`：宽高比变扁（h/w 下降）→ 正分；
- `dy = cy_last − cy_ref`：中心点向下（图像 y 轴向下）→ 正分；
- `border`：最后一个框贴画面边缘（人物正常走出画面的常见特征）；
- `ref` 取消失前 `--track-lost-window`（默认 30）帧内最早的一次检出。

默认 `--track-lost-mode all`：**所有 TRACK_LOST 都保留**，score 写进 `confidence` /
`reliability`，控制端按信道和带宽选工作点；`score ≥ 0.55` 时建议紧急度 HIGH。
需要硬过滤时可用 `--track-lost-mode motion`（score <0.35 不发）或
`motion_no_border`（再要求不贴边）；`--track-lost-suspected-score` 可把高分事件直接
升级成 `SUSPECTED_FALL`，但默认关闭（1.1），以保留语义。

## 5. 可靠性

`confidence` 是来源自己的分数，不是概率。控制端要算“值不值得占带宽”，需要
`P(事件为真 | 证据)`。

`src/common/calibration.py` 提供：

- `reliability_curve(y_true, p)` → 分箱计数、平均预测、真实频率、Brier、ECE；
- `brier_score` / `expected_calibration_error`；
- `IsotonicCalibrator`（PAVA 保序回归）：只假设“分数越高、真实概率不下降”，
  样本量小时比 logistic 稳，也不需要调超参。

**校准必须按场景/机位做**。把 URFD 平视的 0.4 和 MCF 俯视的 0.4 混在一起，得到的
只是两个分布的平均曲线，对任何单一机位都不准。

第一版轨迹上的逐帧代理校准（`confidence` vs `gt_label`，仅统计有框帧）：

| 数据集 | Brier | ECE | n |
|---|---:|---:|---:|
| URFD | 0.598 | 0.646 | 9,252 |
| MCF | 0.356 | 0.303 | 8,208 |

这说明 YOLO confidence **不是**跌倒概率，差异很大；真正上线前要按事件类型/机位校准。
事件层的 `reliability` 字段就是给校准结果留的位置。

`TRACK_LOST` 的 `confidence` 是上面那条规则分数，不是校准概率；它适合**排序**，不适合
直接当概率。评测脚本的 `--min-confidence` 用它做工作点选择（见 §8.3 的曲线）。

## 6. 载荷

| 模式 | 内容 | 示例大小（640×480 合成帧） | 用途 |
|---|---|---:|---|
| `METADATA` | 事件 id/type/urgency/bbox/时间戳 | **63 B** | 控制面；拥塞/差信道时先发 |
| `ROI` | 框裁剪 + padding + 缩放 224 JPEG | **4.8 KB** | 远端确认姿态 |
| `FULL` | 整帧 JPEG | **59.1 KB** | 需要上下文时 |
| `CLIP` | 跌倒前后各 3 s 的片段 | 1~4 MB（M-JPEG） | 人工复核 / 存档；**报警之后**再发 |

> **`CLIP` 不是报警路径**：报警靠 metadata + ROI 先走完，片段是事后低优先级补充，
> 信道不够就丢。片段需要"事前"缓冲，由**传输进程**维护滚动 JPEG 环，不从模型侧的
> 8 槽帧环取——分工与成本见 docs/10 §5.1。板端用 M-JPEG 而非 MP4：每帧独立，
> 丢一个包只坏一帧，也不需要在板端接硬件编码器。

实际大小随画面内容、ROI 大小、压缩质量变化；用
`edge_node.payload.payload_sizes(frame, event)` 在真实帧上实测。

```python
from edge_node.payload import encode_metadata, encode_roi, encode_full, encode_clip
meta_b = encode_metadata(event_snapshot)
roi_b  = encode_roi(frame, event_snapshot["bbox"], max_side=224, quality=70)
full_b = encode_full(frame, quality=80)
clip_b = encode_clip(frames, fps=25)
```

控制端根据 goodput、队列和剩余 deadline 选一个能按时送达的版本；事件层只负责
“能提供什么、各多少字节”。

## 7. 与 8 维事件向量 / 协议的关系

**8 维事件向量布局不变**（`common.event_vector`）：

```
[event_type, confidence, bbox_x1..y2, has_event, severity]
```

它仍然是**逐帧快照**的线上格式；事件流是给控制端的**事件级封装**。两者不是替代关系：

| EventKind | 8 维向量里怎么表达 |
|---|---|
| `PERSON` | `event_type=PERSON`, `has_event=1` |
| `PERSON_ABNORMAL` | 仍可 `PERSON`；异常信息放事件流 meta |
| `TRACK_LOST` | 当前帧无框 → 8 维向量是 `NONE_EVENT`；**只能靠事件流表达** |
| `SUSPECTED_FALL` | `event_type=SUSPECTED`（若该帧有框） |
| `FALL_CONFIRMED` | `event_type=SUSPECTED` + 事件流 `state=CONFIRMED` |
| `BACKGROUND` | `NONE_EVENT` |

协议头/状态向量属于队友的职责。**板端"模型进程 → 传输进程"这一跳的字节布局已经定稿**，
见 **docs/10_模型传输共享内存契约.md**（Header / FrameRecord 512 B / EventSnapshot /
FrameImage 帧环，含读写协议与自检脚本要求）。下面仍是对**线上协议**（UDP 包头）的建议
（**待对齐，不是定稿**）：

- `event_id`、`kind_id`、`urgency_id`、`state_id`；
- `deadline_ms`（由控制端按紧急度/场景设置）；
- `payload_mode`（metadata/ROI/FULL/CLIP）；
- `start_ts` / `last_seen_ts` / `reliability`；
- 控制端 → 事件端：请求某个事件的某个载荷、远端确认/拒绝结果。

## 8. 轨迹格式与评测

### 8.1 目录

```
data/recordings/event_traces/<dataset>/
    per_frame.npz      逐帧证据 + 真值阶段/标签
    gt_events.jsonl    真值跌倒事件
    pred_events.jsonl  事件形成器输出（含 kind_first_frame）
    stream.jsonl       START/UPDATE/CLOSE 事件流
    meta.json          fps、列名、tracker 配置、证据规则
```

`per_frame.npz` 的列（`meta.json` 里也有）：

```
index, timestamp, has_event, pred_kind_id, confidence, severity,
bbox_x1, bbox_y1, bbox_x2, bbox_y2, aspect_ratio, gt_phase, gt_label
```

`gt_phase`: `0=other, 1=pre, 2=during, 3=post`。

### 8.2 生成与评测

```bash
scripts/rk.sh scripts/make_event_traces.py --dataset all
scripts/rk.sh scripts/check_event_tracker.py
scripts/rk.sh scripts/check_payload.py
scripts/rk.sh scripts/check_calibration.py

# 全部告警类型（PERSON_ABNORMAL + TRACK_LOST + SUSPECTED_FALL + FALL_CONFIRMED）

# 只看强告警（单帧几何/确认），用来隔离 TRACK_LOST 的贡献
```

### 8.3 第一版结果（2026-11-16，现有 0.25 帧表）

| 数据集 | 告警口径 | 真值 | 告警事件 | 命中 | 召回 | 精确率 | 误报/min | 提前量中位 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| URFD | 全部（默认，conf≥0） | 30 | 66 | 30 | **1.000** | 0.455 | 5.43 | +0.72 s |
| URFD | conf≥0.30 | 30 | 55 | 30 | **1.000** | 0.545 | 3.77 | +0.72 s |
| URFD | conf≥0.40 | 30 | 52 | 30 | **1.000** | 0.577 | 3.32 | +0.70 s |
| URFD | conf≥0.55 | 30 | 50 | 30 | **1.000** | 0.600 | 3.02 | +0.70 s |
| URFD | 强告警（单帧几何） | 30 | 36 | 27 | 0.900 | 0.750 | 1.36 | +0.90 s |
| MCF | 全部（默认，conf≥0） | 240 | 177 | 163 | **0.679** | 0.921 | 1.37 | +0.56 s |
| MCF | conf≥0.30 | 240 | 137 | 130 | 0.542 | 0.949 | 0.68 | +0.56 s |
| MCF | conf≥0.40 | 240 | 119 | 115 | 0.479 | 0.966 | 0.39 | +0.64 s |
| MCF | conf≥0.55 | 240 | 94 | 92 | 0.383 | 0.979 | 0.20 | +0.72 s |
| MCF | 强告警（单帧几何） | 240 | 21 | 21 | 0.088 | 1.000 | 0.00 | +0.84 s |

> 提前量为正 = 告警晚于真值 onset；负 = 提前。  
> **TRACK_LOST 的评分让控制端有了一个可调工作点**：URFD 在 conf≥0.55 时召回仍是
> 1.000，误报从 5.43/min 降到 3.02/min；MCF 在 conf≥0.30 时精确率从 0.921 升到
> 0.949，召回从 0.679 降到 0.542，再往上就是继续用召回换精确率。  
> MCF 的“全部”里 156/177 是 `TRACK_LOST`；强告警只有 21 个，
> 说明**单帧几何在 MCF 上只能覆盖 8.8% 的事件，TRACK_LOST 把它拉到 67.9%**。
> 但 URFD 的 ADL 结尾仍会产生高分误报（人是正常走出画面），所以控制端不能只看
> “有没有 TRACK_LOST”，还要看分数/紧急度；这也是 §9 里继续加前景证据的理由。
>
> **可选消融**：`--track-lost-mode motion`（硬过滤低分）→ URFD 1.000/0.500/4.52、
> MCF 0.612/0.967/0.49，比默认更保守，适合当规则基线。`--track-lost-suspected-score 0.7`
> 会把高分 TRACK_LOST 升级成 `SUSPECTED_FALL`：MCF 强告警召回 8.8%→**41.7%**
> （精确率 0.99），但 URFD 强告警精确率 0.750→0.536（ADL 高分误报被升级），
> 所以默认关闭。

分阶段（MCF，全部告警口径）：

| 阶段 | 帧数 | 有框率 | 告警率 |
|---|---:|---:|---:|
| pre | 4,880 | 0.693 | 0.014 |
| during | 7,280 | 0.536 | 0.038 |
| post（躺地） | 2,480 | **0.094** | 0.007 |
| other | 744 | 0.936 | 0.011 |

这张表就是“躺地失效”的事件级证据：躺地阶段有框率只有 9.4%，但事件层仍能通过
`TRACK_LOST` 把一部分事件报出来。真正提升静态躺姿召回，还需要前景/模型侧证据（§9）。

## 9. 已知限制与下一步

1. **`TRACK_LOST` 已加运动评分，但仍有极限**：URFD 的 ADL 结尾（人正常走出画面）仍会
   得到不低的分数，单靠“消失前下沉/变扁”分不开“坐下再离开”和“真跌倒”。下一步是加
   “前景 blob 在地面区域/静止”或 ROI 条件；短期则由控制端按 confidence/urgency 丢弃
   低分事件。`motion` / `motion_no_border` 硬过滤是可选的保守基线，不是默认。
2. **可靠性只是代理**：当前用逐帧 confidence 对 gt_label 做曲线；真正需要按事件类型/
   机位校准，并用 `reliability` 字段传给控制端。
3. **“一开始就躺着”未覆盖**：背景减除/轨迹丢失都假设“先看到人”。已躺地场景需要
   微调检测器或启动时的静态审计，建议单独定义。
4. **MCF 帧率约 25fps**（AVI 头写 120fps 不可信），绝对时间指标要注明；帧号在标注区间
   之间不连续，`false_alarms_per_min` 的分母是轨迹帧数，不是完整视频时长。
5. **协议未对齐**：事件流字段/包头属于双方接口；8 维向量布局不变。和队友对齐后再定稿。
