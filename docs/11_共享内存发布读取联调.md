# 模型发布 → WiFi 读取联调

2026-11-21：已实现 Python 实际发布器、摄像头脚本接入、C 读取模块及 `Wifi_Send --shm`
检查入口。这一阶段在 C 端打印记录、复制 BGR 并计算校验值；尚未将真实图片编码后发往 Windows。
此前用户已反馈固定图片 TCP/type=20 与 `wifi_monitor` 联调正常。

## 数据流和边界

```text
cameraApp --/camera_shm + READY/RELEASE--> board_camera_edge.py
           --/edge_infer_shm + flock--> Wifi_Send --shm（本地复制和打印）
```

- 字节布局沿用 [edge_shm.h](../src/edge_node/edge_shm.h) 和
  [edge_shm.py](../src/edge_node/edge_shm.py)，不修改 v1 字段偏移或总大小。
- 默认固定为旋转后 480×640、连续 uint8 BGR，921,600 字节；不是 letterbox RGB，也不是 JPEG。
- 帧记录 64 槽，图像 8 槽，事件表 16 槽；总大小 7,409,024 字节。
- 本轮保留 `event_from_detections()` 的既有逐帧事件向量；EventTracker 尚未接入。
  `best_event_id=0`、`best_reliability=-1`，事件表为空。不能将 severity 当成跌倒概率。
- 源摄像头必须继续收到 RELEASE；下游覆盖环没有 RELEASE。

## 板端真实采集

三个终端使用同一用户运行。摄像头程序默认由 RGA 旋转 270°，不要再增加 Python 旋转。

终端 A：

```bash
./cameraApp 640 480 1000
```

终端 B（模型仓库根目录、已激活 RKNN Python 环境）：

```bash
python3 scripts/board_camera_edge.py \
  --model models/rknn/yolov8n_232.rknn \
  --stride 2 --save-every 0 --publish-shm
```

看到 `publish_shm=True` 后，在终端 C 使用新编译的 WiFi 程序：

```bash
./Wifi_Send --shm
```

也可以提前启动 C 端并增加等待时间：`./Wifi_Send --shm --idle-ms 15000`。
默认等待模型对象和等待新发布的超时均为 3 秒；此超时仅用于提示和退出，不代表模型故障已确认。

正常输出包含：

```text
[shm] seq=... frame_id=... persons=... dets=... flags=... infer_ms=... bgr=921600 image_mismatch=0 skipped=... hash=...
```

`seq` 是发布号，连续递增；`frame_id` 保留摄像头 READY 帧号，stride 跳号正常。
读取“最新帧”时 `seq` 可以跳号，`skipped` 是这次主动未读取的发布数，不等于已被覆盖的记录数。
静态画面可能存在重复 hash，不能据此判断没有发布。

原本不带 `--publish-shm` 的摄像头测试方式继续可用；启用时输出尺寸不符会在归还当前
摄像头槽位后报错退出。模型初始化、运行异常或 SIGINT/SIGTERM 退出均经过资源清理。

## 不使用摄像头的演示

先在终端 A 运行：

```bash
python3 scripts/demo_edge_shm.py --count 200 --fps 30
```

几秒内在终端 B 运行：

```bash
./Wifi_Send --shm --poll-ms 1 --delay-ms 100
```

演示发布合成 BGR，每帧全部字节为发布号 `% 251`，摄像头帧号模拟为发布号的两倍。
读端故意慢读，应看到跳号而写端持续发布；最后读完末条记录后打印 publisher exited。
可用 `--bad-every 10` 每 10 次发布一条 BAD、无图记录。

## 接口与生命周期

[ShmPublisher](../src/edge_node/shm_publisher.py) 只依赖 Python 标准库：

```python
with ShmPublisher() as publisher:
    publisher.update_counters(frames_ready, inference_attempts)
    publisher.publish(record, bgr, started_ns=processing_start_ns)
```

- `publish()` 分配连续发布号，不修改传入 record；参数先在私有缓冲区校验和打包。
- 图像和记录在同一数据锁内复制，`pub_seq` 最后提交；`infer_ms` 包括等待数据锁和复制图片，
  计时终点位于提交记录之前，随后仍有少量提交开销。它不是纯 NPU run 时间。
- 每个选中的推理帧发布一次；解码/推理失败发布 BAD、无图。跳过推理的源帧只更新计数。
- 摄像头时间戳仅在 V4L2 标明 MONOTONIC 时透传并置 `TS_FROM_CAMERA`；否则填 0。
- 本轮暂不写事件快照；C 端可见空事件表。

C 端接口见 `wifi_send/inc/shm_reader.h`：

```c
ShmReader reader = SHM_READER_INITIALIZER;
shm_reader_open(&reader, EDGE_SHM_NAME, EDGE_LOCK_PATH);
/* snapshot.bgr 指向调用方分配的 EDGE_IMG_SIZE 缓冲区。 */
int status = shm_reader_get_latest(&reader, &snapshot);
shm_reader_close(&reader);
```

返回 1 表示复制了一条新记录，包括 BAD、无图；0 表示没有新记录或数据锁暂忙；-1 为错误。
BAD、无图或图片帧号/尺寸不匹配时 `bgr_size=0`，不允许把缓冲区残留图像当成当前帧。
容量不足返回 `ENOBUFS`，不会推进已读取序号，可以补足容量后重新读取。

读端不创建/删除共享对象，不返回 mmap 内的图像指针。拿到的 BGR 是自己的副本，
后续覆盖环不会改变它；复用同一输出缓冲区再次读取时，调用方应结束对上一张图的访问。
头和记录均在同一 flock 内读取，不在锁外轮询普通内存字段。

锁路径 `/tmp/edge_infer.lock` 用于短时读写互斥，另有 `.writer` 生命周期锁防止多写端。
flock 可能短暂等待，但不会等待消费者归还槽位；编码和网络发送必须在锁外。
`img_overwrites` 仅统计图像环正常复用，不能单独证明读端丢图。

正常关闭时标记 `MODEL_EXITED`、取消 READY 并 unlink 共享对象，已映射读端仍可排空末帧。
锁文件保留，防止替换 inode 破坏互斥。重新启动模型后读端需要重新打开对象。
SIGKILL/断电可能留下对象，发布器不会自动覆盖；确认旧进程已退出后显式执行：

```bash
python3 scripts/demo_edge_shm.py --clean
```

存在活跃写端时清理会失败，不删除活动对象。

## 主机验证

从模型仓库运行：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_edge_shm.py
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_camera_publish_flow.py
```

从相邻 `wifi_send` 仓库运行：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 test/test_shm_reader.py
python3 test/test_live_frame.py
```

共享内存测试使用临时文件的真实 MAP_SHARED/flock，验证 Python → C 字节布局、80 次环覆盖、
独立慢读 C 进程的 200 次发布、源图修改与持有副本、重复读取、坏帧、无图、图像不匹配、
容量不足、非法头和序号、双写端、残留清理和退出末帧。它不调用板端 POSIX SHM 或 RKNN。
摄像头流程检查执行真实 `run_camera()`，替换外设和数组计算，验证 stride、推理失败、
每个 READY 恰好一次 RELEASE、初始化失败和尺寸不符时的资源清理。

主机 GCC 9.4.0、SDK GCC 10.3.1 的 C 端严格告警 Release 构建通过。
真实摄像头、RKNN 和板端 `/dev/shm` 的完整链路仍需上板验证。
