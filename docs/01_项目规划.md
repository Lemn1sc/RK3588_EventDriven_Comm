# 项目规划

## 1. 目标

在单块 RK3588 开发板上，构建一个**事件驱动无线通信系统**，以"检测 + 姿态估计级联卸载"（跌倒检测）为典型场景，**定量证明**事件驱动相比周期性传输在带宽、延迟、有效信息比上的优势，并证明 **GRU 控制端相比固定阈值方法的增益**。

## 2. 范围

**做**：
- 事件端（本地轻量检测）
- GRU 控制端（时序 + 信道 → 卸载/传输决策）
- WiFi 传输（事件驱动的 UDP 通信）
- 远端服务（重量级模型精检）
- 对比实验（4 条基线）

**不做（本阶段）**：
- 多板 / 多智能体协作
- 强化学习（GRU 用监督学习训练；RL 作为可选扩展）
- 生产级可靠传输（用轻量重传即可，不做 TCP 级全可靠）

## 3. 核心指标（论文 / 结题数据）

| 指标 | 含义 | 期望结果 |
|------|------|----------|
| 传输率 / 带宽占用 | 传输帧数 / 总帧数 | GRU 方案 5-15%，远低于周期传输 100% |
| 事件检出率 | 真实事件被上报的比例 | 不能漏报关键事件（跌倒） |
| 平均传输延迟 | 事件发生 → 远端确认 | 事件驱动 < 周期采样最大延迟 |
| 误报率 | 无事件却传输的比例 | GRU < 固定阈值 |
| 信道利用效率 | 在信道好时传输的比例 | GRU 能择机传输 |

## 4. 里程碑（相对时间，起点 = 2026-07）

| 阶段 | 目标 | 依赖板子 | 估时 |
|------|------|----------|------|
| M0 无板子准备 | PC 全链路模拟 + GRU 训练 + 实验框架 | 否 | 3-4 周 |
| M1 板端基础 | 板上跑通 yolov8n 检测推理 | 是 | 1-2 天 |
| M2 通信打通 | 板 ↔ PC 真机 WiFi 收发 | 是 | 1-2 天 |
| M3 固定规则版 | 阈值卸载，演示基本优势 | 是 | 1-2 天 |
| M4 GRU 上板 | GRU 转 RKNN 上板决策 | 是 | 3-5 天 |
| M5 对比实验 | 真机四基线对比出数据 | 是 | 1 周 |
| M6 论文 / 结题 | 图表 + 撰写 | 否 | 持续 |

> M0 是当前阶段，几乎覆盖全部算法与系统逻辑；板子到手后 M1-M5 主要是移植与实测。

## 5. 风险与对策

| 风险 | 对策 |
|------|------|
| rknn-toolkit2 版本与板端固件不匹配 | 板子到手第一件事查 `/proc/rknpu/version`，锁定版本 |
| GRU 相比固定阈值增益不明显 | 精心设计"事件突发 + 信道波动"场景放大差异；仿真器可控注入 |
| 跌倒/正常动作区分难 | 用检测框高宽比 + 重心高度变化速率时序特征；必要时远端 pose 兜底 |
| 真机帧率不足 | yolov8n 在 RK3588 NPU 约 20-30fps，够用；不够则降分辨率 |

## 附录：本月月报（已提交）

> 本月完成了课题的整体方案调研与技术选型工作。围绕"事件端—GRU控制端—WiFi传输端"三端架构，调研了多种典型事件场景（视觉监控、传感器融合、语义视频传输、算力卸载等），结合单板硬件条件和课题目标进行了可行性分析。最终确定采用"检测+姿态估计级联卸载"方案：本地 RK3588 运行 YOLOv8n 做人员检测，GRU 编码检测框时序变化判断是否存在异常，仅在疑似异常时通过 WiFi 将帧卸载至远端进行姿态估计确认。同时梳理了 RKNN Model Zoo 中可用的模型资源及部署路径，明确了后续上手步骤。下月计划在板端跑通 YOLOv8n 推理并搭建 WiFi 通信模块。
