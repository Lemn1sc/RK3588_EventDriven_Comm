# `/edge_infer_shm` 使用说明

模型进程写，传输进程读。

头文件 `edge_shm.h` 管的是"字节怎么排"；这份文档管的是"为什么这么排、读的时候要注意什么"。
读到后面如果有个字段觉得多余，大概率是先踩过坑才留下的——第 10 节列了几个常见疑问。

---

## 1. 这块内存解决什么问题

模型每推理一帧，会产生两样性质完全不同的东西：

- **结论**：有没有人、框在哪、有没有事件、有多急。几百字节，每一帧都有。
- **像素**：这一帧的 BGR 原图。将近 1 MB，只有决定要发图时才用得上。

传输端大多数时候只关心结论——要做 GRU 判断、要记日志、要决定值不值得传。
所以这块内存分成两个区：一个放结论，一个放像素，记录里只留一个槽位号把它们连起来。
两块在同一次 `mmap` 里，不是两块共享内存。

---

## 2. 和 `/camera_shm` 的关系

两块内存是独立的，各有各的生产者：

```
cameraApp ──写──> /camera_shm ──读──> 模型进程 ──写──> /edge_infer_shm ──读──> 传输进程
```

模型进程夹在中间：对摄像头是消费者，对传输是生产者。

管理方式不一样，**现有的 `camera_consumer.c` 不能照抄**：

| | `/camera_shm` | `/edge_infer_shm` |
|---|---|---|
| 槽位 | 借出去必须还（`RELEASE`） | **覆盖环，读完什么都不用还** |
| 通知 | socket 发 `READY` | **轮询 `header.pub_seq`** |
| 互斥 | socket 握手 | **`flock` 文件锁** |

写端从不等待读端。读端慢一点最多丢几条记录、或丢掉一张已经被覆盖的图——
这是有意的：模型进程的帧循环不能被传输卡住。

---

## 3. 整体布局

整块对象 7,409,024 字节，四段：

| 段 | 起始偏移 | 大小 | 放什么 |
|---|---:|---:|---|
| Header | `0` | 128 B | 参数、发布序号、计数器 |
| 帧记录 × 64 | `128` | 32 KB | 每推理帧一条，512 B |
| 事件快照 × 16 | `32,896` | 3 KB | 活跃事件，每个 192 B |
| 图像环 × 8 | `35,968` | 7.03 MB | 32 B 头 + 921,600 B BGR |

定位规则有一点点差别，记一下：

```
第 n 条记录      → 128        + ((n - 1) % 64) * 512      // n 从 1 开始
事件 event_id    → 32896      + (event_id % 16) * 192
帧环第 slot 槽   → 35968      + slot * 921,632
```

头文件里给了 `edge_rec_offset()` / `edge_ev_offset()` / `edge_img_offset()`，
直接调用就行，别自己写这几个数。

---

## 4. Header：读端先看什么

`edge_shm_header` 128 字节。读端启动时先校验，运行时主要看两个字段。

**启动校验**（不对就别读了，直接报错退出）：

- `magic == 0x45444731`，`version == 1`
- `total_size == 7409024`，以及 `n_rec / n_ev / n_img / img_w / img_h` 是否和预期一致

**运行时看**：

- `pub_seq`：已经发布了多少条记录。**轮询它就等于"有没有新数据"**，不需要别的通知。
- `img_seq`：帧环发布了多少帧，用来算槽位。
- `last_update_ts_ns`：写端最后一次发布的时间。超过 2 秒没变，说明模型进程卡住或退出了。

**排查用**：

| 字段 | 什么时候有用 |
|---|---|
| `frames_ready` | 摄像头一共给了多少帧；和 `frames_inferred` 对比能看出实际 stride |
| `frames_inferred` | 真正推理了多少帧（正常应约等于 `pub_seq`） |
| `frames_bad` | 解码/推理失败的次数 |
| `img_overwrites` | 帧环被覆盖了几次——**读端落后的直接证据** |
| `last_error` | 最近一次错误码，含义由写端定义 |

---

## 5. 帧记录：一帧的结论

每条记录 512 字节，对应**一次推理**。被 stride 跳过的帧不会发布，所以 `frame_id` 会跳号——
看到跳号是正常的，不是丢数据；丢数据要看 `seq`。

字段按用途分五组。

### 5.1 身份与时序

| 偏移 | 字段 | 含义 |
|---:|---|---|
| 0 | `seq` | 发布号，从 1 连续递增。**判断漏帧只看它** |
| 8 | `frame_id` | 摄像头那边的帧号（就是 cameraApp 的 `frame_id`），会跳号 |
| 16 | `capture_ts_ns` | 摄像头采到这一帧的时刻；无效时是 0 |
| 24 | `publish_ts_ns` | 模型发布这条记录的时刻 |
| 32 | `infer_ms` | 这一帧从取图到发布的耗时 |

`publish_ts_ns - capture_ts_ns` 是板上处理时延。远端回来时带回 `recv_ts`，
再减 `capture_ts_ns` 就是端到端时延。**没有 `capture_ts_ns`，80 ms 到底花在哪就说不清了。**

`seq` 和 `frame_id` 同时存在不是冗余：`seq` 是模型自己的发布节奏（15 Hz，连续），
`frame_id` 是摄像头的物理帧号（30 Hz，会跳）。判断完整性用前者，对外指认"哪一帧"用后者。

### 5.2 状态位

`flags` 在第 36 字节（`uint32_t`）：

| 位 | 名称 | 含义 |
|---:|---|---|
| 0 | `INFERRED` | 这帧推理成功 |
| 1 | `BAD_FRAME` | 解码/推理失败，后面的字段都不可信 |
| 2 | `NO_PERSON` | 这帧没有人 |
| 3 | `TS_FROM_CAMERA` | `capture_ts_ns` 来自摄像头；没置位时它是写端补的时刻 |
| 4 | `TRACKER_ERROR` | 事件层出错，`best_*` 不可信 |

**读之前先看 `BAD_FRAME`**，否则会把一整条全零的记录当成"画面里没人"。

### 5.3 检测结果

| 偏移 | 字段 | 含义 |
|---:|---|---|
| 40 | `n_det` | `dets[]` 里有效的条数，0~6 |
| 42 | `n_person` | 这一帧人的总数（**截断前**） |
| 44 | `det_total` | 所有检测框的总数（截断前） |
| 46 | `img_slot` | 这帧图像在帧环的槽位；`0xFFFF` 表示没有图 |
| 128 | `dets[6]` | 每个 24 B：`cls(u16) / pad(u16) / conf(f32) / x1 y1 x2 y2(f32)` |

`dets` 的入选顺序是固定的：**先放所有 person（`cls == 0`），按置信度降序，最多 6 个；
不够 6 个再用其他类别补满**。所以 `dets[0]` 不一定是画面里置信度最高的框，
但一定是最值得关注的人。`det_total > n_det` 说明发生了截断。

坐标是归一化的，基准是**旋转后的摄像头原图**（当前 480×640），不是 letterbox 后的 640×640。
要像素坐标就乘 `img_w / img_h`。

### 5.4 事件向量与主目标特征

| 偏移 | 字段 | 含义 |
|---:|---|---|
| 48 | `event_vector[8]` | `[类型, 置信度, x1, y1, x2, y2, 有无事件, severity]` |
| 80 | `aspect` | 主目标高/宽 |
| 84 | `cx` `cy` | 主目标归一化中心 |
| 92 | `w` `h` | 主目标归一化宽高 |
| 100 | `area_ratio` | 主目标框面积占画面比例 |

前 6 个浮点可以直接还原主目标框：`x1 = cx - w/2`，以此类推。
它们看起来能从 `event_vector` 算出来，放在这里是让 GRU 的状态向量少做一步，
也保证"主目标"的定义只有一处。

**注意主目标不等于 `dets[0]`**：主目标取的是 severity 最高的那个，
而 `dets` 是按置信度排的。主目标可能不在 `dets` 里（被截断时），所以裁 ROI 优先用 `cx/cy/w/h`。

### 5.5 事件上下文

| 偏移 | 字段 | 含义 |
|---:|---|---|
| 104 | `best_event_id` | 当前最该关注的事件；`0` 表示没有 |
| 108 | `best_kind` | 事件类型 |
| 109 | `best_state` | `CANDIDATE / ACTIVE / CONFIRMED / EXPIRED` |
| 110 | `best_urgency` | 建议紧急度 |
| 112 | `best_conf` | 事件层分数（可能是规则分，**不是概率**） |
| 116 | `best_reliability` | 校准后的概率；没有校准时是 `-1` |
| 120 | `kind_first_ts_ns` | 当前事件类型第一次出现的时刻 |
| 128 | `dets[6]` | 检测框，格式见 5.3 |
| 272 | `reserved[240]` | 保留，写端保证是 0 |

两个字段容易被误读：

- `best_conf` 和 `best_reliability` 是两回事。前者可能是 `TRACK_LOST` 的规则分，
  适合排序；后者才是"这件事为真的概率"。没校准就是 `-1`，**不能当 0 用**。
- `kind_first_ts_ns` 不是事件开始时间，而是**"从此刻起它才算告警"**。
  一个人的事件可能先是 `PERSON`，两秒后才升级成 `SUSPECTED_FALL`；
  算预警提前量要用后者，用 `start_ts` 会虚报。

### 5.6 一个需要记住的区分

`event_vector` 是**逐帧的检测快照**，`best_*` 是**事件层面的判断**，两者不能互相替代。
最典型的是人躺下之后检测器失效的那一帧：`event_vector` 里是 `NONE_EVENT`
（确实没有框），但 `best_kind` 是 `TRACK_LOST`、紧急度是 HIGH。

如果只看 `event_vector`，这一帧和"画面本来就没人"长得一模一样。

## 6. 事件快照：一次能看到多个事件

一个帧记录只能装下"最该关注的那个"，但调度有时候要同时知道两件事：
A 正在疑似跌倒，B 只是正常经过。所以另有一张 16 槽的事件表。

| 偏移 | 字段 | 说明 |
|---:|---|---|
| 0 | `seq` | 事件表整体的发布号 |
| 8 | `event_id` | `0` 表示空槽 |
| 12 | `kind` `state` `urgency` | 类型 / 状态 / 紧急度 |
| 16 | `start_ts_ns` | 事件第一次出现（可能还是 `PERSON`） |
| 24 | `last_seen_ts_ns` | 最后一次证据 |
| 32 | `kind_first_ts_ns` | 当前类型第一次出现（告警起点） |
| 40 | `confidence` | 当前分数 |
| 44 | `peak_confidence` | 峰值——复盘时看这个，当前值会被后来的证据覆盖 |
| 48 | `reliability` | 校准概率，未校准为 `-1` |
| 52 | `hits` | 命中次数，用来判断"偶发"还是"稳定" |
| 56 | `bbox[4]` | 最后一次位置；人消失后仍能去那里裁图 |

槽位是 `event_id % 16`。事件关闭时写端把 `kind` 清 0，读端据此跳过。

## 7. 图像环：像素在哪

8 个槽，每槽 32 字节头 + 921,600 字节 BGR：

| 偏移 | 字段 |
|---:|---|
| 0 | `seq` |
| 8 | `frame_id` |
| 16 | `capture_ts_ns` |
| 24 | `w` |
| 28 | `h` |
| 32 | BGR 像素，行跨度 `w * 3` |

存的是**原始 BGR**，不是 NV12、不是 JPEG。写端已经转好了，你们直接裁 ROI 就能编码。

取图的正确顺序：

```c
const edge_frame_record *rec =
    (const edge_frame_record *)(base + edge_rec_offset(hdr->pub_seq));

if (rec->img_slot != EDGE_IMG_SLOT_NONE && rec->img_slot < EDGE_N_IMG) {
    uint64_t off = edge_img_offset(rec->img_slot);
    const edge_image_meta *meta = (const edge_image_meta *)(base + off);

    if (meta->frame_id == rec->frame_id) {          /* 图还在 */
        const uint8_t *bgr = base + off + sizeof(edge_image_meta);
        /* 裁 ROI → JPEG → 发送 */
    } else {
        /* 图已经被 8 帧之后的内容覆盖了 */
    }
}
```

`img_slot` 只负责**定位**，`frame_id` 才负责**校验**。只按槽位读会读到别人的图——
8 个槽在 15 fps 下只能撑 0.5 秒。

图被覆盖时怎么办？两个选择：退回帧环里最新的一帧，或者这一次不发图。
记录本身永远有效，事件、框、置信度都还在。

## 8. 读写规则

### 8.1 锁

写端每次发布、读端每次读取，都要拿 `flock("/tmp/edge_infer.lock")`。
写端持锁不到 1 毫秒，你们那边只要别在锁里做 JPEG 编码就行——
需要慢操作时，先把记录和图像拷到本地缓冲，再解锁处理。

### 8.2 轮询

```c
uint64_t last = 0;
for (;;) {
    edge_frame_record rec;
    uint64_t n;

    lock();
    n = hdr->pub_seq;
    if (n > last) {
        uint64_t s = last + 1;
        if (n - s >= EDGE_N_REC) {          /* 中间的被覆盖了，只能从最新附近开始 */
            s = n - EDGE_N_REC + 1;
        }
        memcpy(&rec, base + edge_rec_offset(s), sizeof rec);
        unlock();

        if (rec.seq == s) {                 /* 还是这条，可以放心用 */
            handle(&rec);                   /* 编码之类的慢操作放在锁外 */
            last = s;
        } else {
            last = n;                       /* 连 s 都被覆盖了，跳到最新 */
        }
    } else {
        unlock();
        usleep(1000);
    }
}
```

- `n - last > 1`：中间漏了几条（读端被调度阻塞了，或者写端跑得快）。
- `n - last > 64`：漏掉的那些已经被覆盖，只能从最新的附近开始。
- 每次拿到的记录都要核对 `seq`，这是"我读到的还是这条吗"的唯一证据。

轮询间隔 1 毫秒就够了。单帧推理本身 68 毫秒，晚 1 毫秒没有意义。

## 9. 数值约定

| 约定 | 说明 |
|---|---|
| 时间 | 全部是 `CLOCK_MONOTONIC` 纳秒 |
| 坐标 | 归一化到旋转后的原图（480×640），不是 letterbox 图 |
| 无效值 | 不会出现 `NaN` / `Inf`；没有框就 `n_det = 0`，没有事件就 `best_event_id = 0` |
| `reliability` | 未校准时是 `-1`，不是 `0` |
| `img_slot` | `0xFFFF` 表示没有图 |
| 字节序 | 小端（RK3588 原生）。共享内存**不做**网络字节序转换 |

## 10. 几个常见疑问

**Q：为什么读完不用 RELEASE？**
因为写端不等你。`/camera_shm` 是摄像头流水线，槽位是稀缺资源，必须还；
这里是一块"最新状态"的黑板，过期就被下一帧擦掉，没有归还的概念。
如果照搬 RELEASE，写端会等一个永远不会来的消息。

**Q：为什么图不直接塞进记录？**
一条记录 512 B，一帧图 921,600 B，差 1800 倍。读端只做决策时不该被迫搬 1 MB；
记录要 64 槽历史（4.3 秒），图只要 8 槽，两者深度不一样；
而且坏帧、无框帧就是"有记录、没图"，这个状态需要能被表达。
详细理由见 README 的对应小节。

**Q：为什么记录 64 槽，图才 8 槽？**
记录小，深一点可以让 GRU 拿到 4 秒的上下文；
图大，读端只要保证"事件这一刻的图还在"就够了。更早的画面由传输端自己的滚动缓冲负责。

**Q：读着读着图变了怎么办？**
`frame_id` 对不上就是变了，按第 7 节处理。永远不要"读之前检查一次，然后假设它不变"。

**Q：没有 socket，会不会有延迟？**
轮询 1 ms，实际延迟远小于推理本身的 68 ms。真要事件驱动，可以加一个门铃消息，
但共享内存布局不用动。

---

## 11. 改字段的规矩

1. 已有字段的偏移和宽度**不动**；
2. 加字段只能用 `reserved`，并在头文件里登记；
3. 删字段、改类型、改槽位数 → `version` 加一，读端遇到不认识的版本直接拒绝；
4. 头文件里的 `_Static_assert` 不要删——它在你们的编译期挡这类错误。

改了之后跑一下包里那个布局探针，和我们的 Python 侧对一遍：

```bash
cc -std=c11 -Wall -Wextra -Werror -I . check_edge_shm_layout.c -o layout && ./layout
```
