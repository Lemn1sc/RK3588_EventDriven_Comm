event_rule_engine.py

  这是“边缘端本地判断规则”的核心文件。

  路径：python project/event_rule_engine.py:1

  它负责根据每一帧的人体框判断是否要通信。现在实现的规则就是你说的那几条：

  - 无人：no_person，不通信
  - 有人且人体框高宽比稳定：stable_normal，不通信
  - 人体框突然变宽、变矮：fall_suspicious，触发通信
  - 人长时间几乎不动：static_too_long，触发通信
  - 进入危险区域：danger_zone，触发通信

  以后你训练好 GRU 后，可以把这个文件里的规则判断替换成 GRU 推理。也就是说，它现在是“GRU 的规则替身”。

  event_chain_demo.py

  这是“整条链路的运行脚本”。

  路径：python project/event_chain_demo.py:1

  它做三件事：

  1. 模拟边缘端产生视频帧数据
  2. 调用 event_rule_engine.py 判断是否触发通信
  3. 如果触发，就通过 TCP 发给模拟 PC 端

  它可以用三种模式运行：

  python "python project\event_chain_demo.py" demo

  单机同时模拟 PC 端和边缘端。

  python "python project\event_chain_demo.py" server

  只运行 PC 端。

  python "python project\event_chain_demo.py" edge

  只运行边缘端。

  以后你要接真实摄像头，主要改这个文件里的 build_synthetic_stream()，把模拟人体框换成 YOLO 或其他检测模型输出的人体框。

  edge_frame_log.csv

  这是“边缘端每一帧的记录”。

  路径：python project/edge_frame_log.csv:1

  它记录了每一帧的状态，不管有没有触发通信都会记录。这个文件很重要，因为它以后可以变成 GRU 训练数据。

  里面的字段大致是：

  - frame_id：第几帧
  - timestamp：时间
  - person_present：有没有人
  - bbox：人体框坐标
  - in_danger_zone：是否进入危险区域
  - trigger：是否触发通信
  - reason：规则判断结果
  - stable：高宽比是否稳定
  - motion_px：人体框中心移动距离
  - aspect_ratio：人体框宽高比
  - static_seconds：静止持续时间

  以后训练 GRU 时，可以把 aspect_ratio、motion_px、bbox 的宽高变化、static_seconds 等作为输入特征，把 trigger/reason 作
  为标签雏形。

  pc_event_log.jsonl

  这是“PC 端收到的事件记录”。

  路径：python project/pc_event_log.jsonl:1

  它只记录边缘端真正发来的事件，不记录正常帧。

  比如：

  - 疑似跌倒事件
  - 静止超时事件
  - 危险区域事件

  这个文件的意义是：证明通信不是每帧都发，而是“事件触发才发”。这正是你们项目的核心思想。
